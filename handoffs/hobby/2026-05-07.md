### #136 / #137 ... brain over HTTP + Brain browser

Three new endpoints under `/api/v1/agents/:name/brain`:
- `GET /brain` lists notes (filters: type, tag, limit). Returns lossy DTOs (240-char preview, no full body) so the list view stays small.
- `GET /brain/search?q=` is FTS5-backed via `BrainIndex.openReadOnlyAtPath`. Falls back to a one-shot in-memory list-scan when the index file does not exist yet (a freshly-installed Agent whose AgentProcess never ran). Response carries `mode: 'fts' | 'fallback'` so the UI can show which path served the result.
- `GET /brain/note/:slug` returns the full note. 404 with code `brain_note_not_found` for missing slugs.

The web screen at `/agent/:name/brain` is a two-pane V2 Keyboard Triage variant: list on the left, focused-note detail on the right. Typing in the search box switches to FTS mode and shows snippets. j/k cycles the focused row when no input is focused. The mode chip shows FTS5 vs FALLBACK so the operator can tell which path served the result.

### #138 / #139 ... schedules CRUD over HTTP + Schedule editor

Four new endpoints:
- `GET /schedules` lists.
- `POST /schedules` creates (validates cron via `CronExpressionParser`; bad cron surfaces as 422 `schedule_invalid`).
- `PATCH /schedules/:id` toggles enabled.
- `DELETE /schedules/:id` removes.

Each mutating endpoint calls `supervisor.getScheduler().reload()` so live timers re-arm without a daemon bounce. Mirrors the CLI's `cli.scheduler.reload` RPC.

Web screen has a list-on-top + create-form-below layout. Timing toggle (CRON | INTERVAL chips) switches the form. Disabled rows dim but stay visible so re-enable is one click. v1 = delete + recreate to edit; an in-place edit form is a polish item.

### #140 ... Tools screen + tools endpoint

`GET /api/v1/agents/:name/tools` returns:
- `mcp_servers[]` from the Identity (lossy DTO: drops command-line args + static headers + SecretRef values; preserves names, transport, command, url, env_keys, auth_kind so the UI can show "uses GMAIL_OAUTH_TOKEN" without exposing values).
- `health: ToolHealthSummary` aggregated off Brain run records via the existing `aggregateToolHealth`.

Tolerates malformed Identity + missing brain dir; the screen renders empty states rather than 500ing. The "HOW TO ADD" callout points users at the CLI for tool installation, OAuth login, Skill install, Extension install ... web-app surface for those is deferred.

### #143 ... interaction surfaces

The web app had been read-only for agent state. Doug asked for "wire up a way to interact with them and build out the brain a little bit." #143 added two write paths:

- **`POST /api/v1/agents/:name/tasks`** ... enqueues a pending TaskRecord via TaskStore. The running AgentLoop picks it up next tick. Body `{ title?, body, priority? }`; auto-derives a 60-char title from the body when none supplied.
- **`POST /api/v1/agents/:name/brain`** ... writes a brain note via `BrainStore.write`. Slug is upsert-style when supplied; auto-derived (with collision suffix) otherwise. Returns 201 (created) or 200 (updated) with the resulting BrainNote DTO.

Web surface: SEND TASK card on AgentDetail (above Budget snapshot), `+ Note` button on BrainScreen header that toggles a Compose card with title + body + tags. On success the brain queries invalidate and the new slug auto-selects.

## Notes for future-me

- Two rebase-conflict episodes today. PRs #140 and #143 both hit conflicts because they touched AgentDetailScreen.tsx + router.tsx alongside other in-flight PRs. Pattern to remember: when stacking PRs, the AgentDetail header chips and `<Routes>` declarations are shared edit surfaces. If two PRs both add chip links, sequence them or coordinate the merge.
- Missed merge-conflict markers slipped past local verify into CI on #140's first run because I committed without re-grepping for `<<<<<<<`. Now hardened: always `grep -rn '<<<<<<< \|>>>>>>> '` after a rebase.
- The Brain endpoint's FTS-fallback path is real and hit on freshly-installed Agents whose AgentProcess never ran. The `mode` chip on the screen surfaces it; useful for debugging "search returns nothing" reports later.
- The `+ Note` UI uses the existing `BrainStore.write` slug-derivation + collision-suffix path. Same write same slug twice creates `<slug>-2`. Don't add deduplication to the HTTP path; the store handles it.
- Settings is intentionally minimal at v1. The "WHAT YOU CAN DO IN THE CLI" card is a feature, not a placeholder ... it tells users which surfaces are CLI-only without making them dig through `2200 --help`.
- The pulse dot was already wired (Epic 15 Phase A); Phase C didn't touch it. The animation cadence comes from `intensity` (smoothed [0,1] field on the pulse DTO) and the period scales from 2000ms (intensity 0) → 500ms (intensity 1).
- Daemon restart picks up new web bundles automatically since the static dir is resolved at startup. `2200 daemon stop && 2200 daemon start` is the v1 reload UX.

## Reflection

Eight PRs in one session is a step beyond yesterday's seven. What enabled the throughput:

1. **Substrate-then-screen pairing.** Each Phase C surface (Brain, Schedules, Tools) shipped as a backend PR followed by a UI PR. Each pair was small enough to land in one verify cycle and never blocked the other.
2. **Decide-and-tell on the AgentDetail completion.** "MORE FOR THIS AGENT" was a smaller scope than "inline previews of brain/schedules/tools." Picking the smaller one and landing it kept the day moving without losing user value.
3. **User-driven mid-session pivot.** Doug's "wire up a way to interact" feedback came after he started testing in the browser. Building the interact surfaces in response is the cleanest example of the build-with-feedback loop that 2200 is meant to support for its eventual users.
4. **Rebase-conflict cost is real.** Two PRs hit conflicts because they touched the same shared files (router.tsx, AgentDetailScreen.tsx). Both resolved cleanly but cost ~10 minutes each. For Phase D, sequencing chip-additions through one shared PR (or accepting that AgentDetail is a lock-step file) will cut that.
5. **Daemon restart is a smooth reload UX.** Each PR's UI changes were testable seconds after merge via `daemon stop && start`. No need for a hot-reload dev mode at v1.
