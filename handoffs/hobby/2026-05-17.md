## What shipped (in order)

### Boot-time gateway recovery + orphan sweep (`a945215`)

Closed the substrate gap that bit us twice on 2026-05-16: connector gateways died on supervisor restart with no auto-recovery. Now:

- After `fastify.listen`, the supervisor walks installed Extensions + per-Agent identity bindings and spawns the gateways that should be running (per-Agent for Discord, per-Extension for WhatsApp Inbox).
- Before recovery, an orphan sweep walks `<home>/state/extensions/*/gateway.json` and SIGTERMs any pids still alive (the SIGKILL'd-prior-supervisor case). 200ms grace, then spawn fresh so the new gateway doesn't contend with the orphan for the same bot token / device pair.
- Verified end-to-end via daemon stop/start; Discord (Simon) + WhatsApp (extension-scope) both came back automatically.

### Settings → Doctor tab + shutdown-race fix (`dc3d3bb`)

Doctor surface: substrate self-healing as a first-class UI. Polls `/api/v1/doctor/diagnose` every 10s, renders issues with severity + per-issue Fix button. Initial checks: errored-Agents-recoverable, errored-Agents-unknown (report-only), connector-gateway-missing, pending-credential-orphaned.

Same commit fixes the shutdown-race that wedged Jodin: previously an Agent exiting with `code=null signal=null` during daemon shutdown was flagged `errored` with `will_revive_next_boot=false`. New rule: `isCrash` iff `(code !== null && code !== 0) || (signal !== null && signal !== 'SIGTERM')`. Anything else is benign during intentional shutdown. Verified: post-fix, all four Agents survive daemon restart in `running` state.

### Live model poll per saved endpoint (`dd854bd`)

Each saved custom endpoint polls its upstream `/v1/models` every 30s. New `GET /api/v1/settings/endpoints/:id/models` resolves the saved api_key server-side. Endpoint row gains a status pill (`N live` / `probing` / `unreachable`), a SELECTED model chip list (drift from upstream flagged in red), and an AVAILABLE NOW chip list (ghost-style for served-but-not-yet-selected models). Doug brought up the GB10 ("Pud" at `100.104.125.98:8000/v1`, Tailscale CGNAT) and the row immediately started reporting `1 live` with `qwen3-30b` visible.

### Build an Agent: enumerate custom endpoints + live models (`647a5bc`)

The Onboarding picker only knew about built-in providers (anthropic, deepseek, etc.). Doug's new GB10 endpoint was invisible. Fixed by union-ing `/settings/providers` with `/settings/endpoints` and rendering them in two `<optgroup>`s ("Providers" / "Custom endpoints"). Then a second pass made the model list use the live `/v1/models` output (via `useQueries` per endpoint) so an endpoint the operator hasn't manually "Edit"-ed to select a model still shows its actual served model. Endpoint labels read `(N live)` / `(saved)` / `(unreachable)`.

### Stale-controlled-component fix on the picker (`00a6c20`)

The Begin button was greyed out even though Doug had picked Pud + `qwen3-30b`. Cause: when he selected Pud BEFORE the live `/v1/models` query had resolved, the onChange callback read `models[0]` as `undefined` and `modelId` stayed `''`. Live query resolved later, dropdown displayed the model, but the React-controlled `value=''` didn't match any option, Begin stayed disabled with no signal. Added an effect that re-syncs `modelId` to the first option when the selected option's model list lands asynchronously.

### OpenAIProvider baseUrl normalization (`be3ef1d`)

Build an Agent threw `internal_error: Internal server error` on the second interview question. Cause: `OpenAIProvider` was unconditionally appending `/v1/chat/completions` to `baseUrl`. Doug's saved baseUrl is `http://100.104.125.98:8000/v1` (the standard OpenAI-client shape that vLLM / Ollama / LM Studio docs print), so the resulting URL was `.../v1/v1/chat/completions` and upstream returned a confusing "model not found (404)." Now: strip trailing slashes, check for `/v1` suffix, append only `/chat/completions` if it's already there. Both URL shapes (`http://host:8000` and `http://host:8000/v1`) resolve to the same canonical endpoint. 4 new tests.

### Default new Agent to `studio` when multiple pubs exist + rename "spawn" → "build" (`183340e`)

Build an Agent's Confirm step threw `multiple pubs exist; please specify --pub <name>` for any multi-pub install. The HTTP confirm endpoint doesn't surface a pub picker, so the flow was unrecoverable. Fixed in `pickTargetPub`: prefer `studio` (canonical team room) when present, fall back to alphabetically-first. Deterministic. Same commit dropped the sci-fi tone Doug flagged: button now reads "Confirm + build" / "Building..." instead of "Confirm + spawn" / "Spawning...". 9 supervisor tests pass.

### Native-tool-use fallback in OpenAIProvider (`d4e9340`)

David's first chat threw an LlmError because the GB10's vLLM wasn't started with `--enable-auto-tool-choice --tool-call-parser hermes`. The error body is precise enough to detect; now: on a 400 whose body matches `looksLikeNativeToolUseRejection()`, the provider logs a one-line warning naming the missing server flags, drops the `tools` / `tool_choice` fields, retries once, and caches `nativeToolsDisabled = true` so subsequent calls skip the spec entirely. The agent loop's textual JSON-block tool parser is the universal fallback. Doug restarted vLLM with the right flags in parallel and got David working with native tools; the fallback covers any future server-misconfig case. 3 new tests.

### Reaction whitelist mismatch (`d5b8332`)

After David's intro, Doug `@-mentioned` Simon, Hobby, and Jodin to say hi. Only Jodin replied. Diagnosis: Simon and Hobby tried to `pub_react` with `✓` (bare check) and `❤️` (heart); OpenPub's curated whitelist accepts `✅` (check button) and has no heart. Both were rejected with `INVALID_REACTION`, the Agents retried with cosmetic variants, spiraled, ended the task with no text reply.

Three-layer fix:
1. System prompt teaches the canonical OpenPub whitelist and tells the Agent: if `INVALID_REACTION`, switch to `pub_send` immediately ... do NOT retry with a different emoji.
2. `pub_react` tool normalizes common variants server-side: `✓ → ✅`, `❤️ → 🔥`, `✘ → ❌`. Old habits still land.
3. Loop injects a forcing directive into history when `pub_react` returns `INVALID_REACTION` so the model unambiguously pivots to text. Stops the spiral.

3 new tests (12 in pub-tools). Inboxed Poe at [[../../inbox/poe/2026-05-17-reactions-any-emoji]] proposing OpenPub drop the whitelist entirely (Discord-style any-emoji), per Doug's preference. The 2200-side fix is the defensive layer; the OpenPub change is the cleaner long-term move.

### Tool-trigger quick reference + credential card persists across reload (`40ed9c1`)

Two symptoms from David's session:

1. David didn't know to call `credential_request` when Doug said "I'm about to give you an API key. Ask me for it." Replied "I'm ready to receive the API key" and waited for Doug to send the value as chat text. The credential_request rule was buried in a long load-bearing rules section; smaller models (Qwen 3 30B) didn't surface it. Fix: new "Tool triggers (quick reference)" section near the top of the system prompt with concrete trigger phrases:
   - "API key / token / password / secret" → `credential_request`
   - "ask X and tell me what they say" → `task_await_response`
   - "delegate this to Y" → `task_create_for_agent`
   - "remember / take a note" → `brain_write`
   - "call this API" → `http_request`
   - "schedule X" → `schedule_add`
   Plus discord/whatsapp/notification triggers. Closes with: "Asking the operator to do something a tool can do is a bug."

2. Page reload reverted the credential card from "Provided / verified" back to the input form even though the credential had already been sealed. Cause: card initialized `resolved.state` from the embedded envelope in the chat message body (always `'pending'`, written at request-creation time); WS pushes state changes not snapshots, so a fresh load with no events saw the pending envelope. Fix: card now fetches `credentialRequestList(agent)` on mount and overrides `resolved` with the server's authoritative state. Falls back to the embedded envelope on fetch failure.
