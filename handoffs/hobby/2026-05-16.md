### Afternoon ... build the substrate

Sequenced as: schemas → routing → inbound endpoint → connector package → outbound tool → live test.

**Schemas (`src/runtime/extensions/types.ts`, `src/runtime/identity/types.ts`, `src/runtime/agent/task/types.ts`).** Added:

- `ConnectorManifestBlockSchema` ... the optional `connector` block in an Extension's manifest (`id, label, blurb, docs_path, auth_model, tos_acknowledgment`).
- `GatewayHookSchema` ... new `hooks.gateway` entry on the manifest (script path + restart_policy).
- `AgentConnectorBindingSchema` ... new `connectors:` block in Identity frontmatter (per-Agent per-connector binding with allowlist + policies). Default DM policy: `pairing`. Default group policy: `allowlist`. Per Doug's call.
- `TaskSource` discriminated union gains a `connector` variant carrying `{connector_id, conversation_id, sender_id, account, sender_display_name?}`.

All schema additions are non-breaking (defaults). Three test fixtures gained `connectors: []` to satisfy the now-required field in `IdentityFrontmatter` output type.

**Routing (`src/runtime/connectors/router.ts`).** Pure-function `routeInbound({event, identities, mentionDetector?})` returning per-Agent decisions: `pass` / `pair` / `block` with reason codes. The supervisor's HTTP handler is the wake source; per-Agent `ConnectorWakeSource` is unnecessary because inbound is webhook-pushed, not subscribed.

**Inbound endpoint (`src/runtime/http/server.ts`).** New `POST /api/v1/connectors/:connector_id/inbound`. Validates payload (Zod), enumerates known Identities, runs router, creates synthetic tasks on Agents that pass. Pairing requests log-only for v1 (operator-notification fan-out is a follow-on). Loopback-only; bearer-token gating deferred to the install-flow work.

**WhatsApp connector package (`apps/whatsapp-connector/`).** New pnpm workspace package, depends on `@whiskeysockets/baileys@7.0.0-rc11` + `qrcode-terminal`. Single entry script `src/gateway.ts` (~290 lines):

- `useMultiFileAuthState(AUTH_DIR)` persists Baileys session across restarts (so QR scan only happens once).
- On `connection.update` with a `qr`, the gateway prints an ASCII QR to stderr via `qrcode-terminal`.
- On `messages.upsert`, the gateway extracts the text + sender JID + conversation JID, normalizes to a `ConnectorInboundEvent`, POSTs to the supervisor's `/api/v1/connectors/whatsapp/inbound`. Self-echo and status broadcasts filtered.
- HTTP listener bound to `127.0.0.1:GATEWAY_PORT` exposing `POST /outbound` ... receives `{to, body}`, calls Baileys `sock.sendMessage(to, {text})`. The `whatsapp_send` baseline tool POSTs here.
- At startup the gateway writes `<home>/state/extensions/whatsapp/gateway.json` (port + account + pid + started_at) so the `whatsapp_send` tool can discover the port. Removed on SIGTERM/SIGINT.

**Outbound tool (`src/runtime/tools/baseline/whatsapp.ts`).** New `whatsapp_send` baseline tool ... reads gateway.json, POSTs `{to, body}` to the gateway, returns `{status, message_id, to}`. Throws `gateway_not_running` if the file is missing or the gateway is unreachable. Baseline tool count is now 40 (`BASELINE_TOOL_NAMES` bumped from 39).

### Late afternoon ... the Connector Store conversation

Doug surfaced the right next-level concern: install + auth should be web-driven, not terminal-driven. Asked for an architectural map. I outlined:

- **Distribution:** npm for packages + a small `catalog.json` on 2200.ai for the curated list. Don't reinvent npm. Pinned versions + sha256 checksums in catalog entries.
- **Install pipeline:** new supervisor HTTP endpoint `POST /api/v1/extensions/install` that resolves `catalog:whatsapp` or `npm:@2200/whatsapp` or `path:/local/dir`, runs install in background, broadcasts WS progress events.
- **Web Store UI:** new `/extensions` screen with three tabs (Installed / Connectors / All). Per-card install button → permissions modal → ToS-ack modal → background install with progress → auth flow opens.
- **Per-auth-model walkthrough:** dispatched off `connector.auth_model`. `qr_pair` (WhatsApp) renders a real QR image, watches a WS event for connection.update. `oauth` (Slack) redirects + handles callback. `bot_token` / `api_key` (Telegram / Discord) form input → vault.
- **Security:** catalog is the trust boundary (vetted + signed + version-pinned + checksumed). Permission prompts at install (Phase B already). "Unvetted" lane for raw npm with a big warning.

I recommended Path A (finish today's terminal-QR substrate test in 5 min to validate the runtime pieces, then build the Store as presentation on top of a known-good foundation). Doug paused there and asked me to lock the documentation first ... so the substrate live-test is parked for the next session.
