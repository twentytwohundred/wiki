### #103 — scheduler flaky-test fix

Microtask race in the test, not the production code. `fire()` does:

```
await enqueueSyntheticTask
await recordFired
arm()  // synchronous after recordFired's promise resolves
```

The test's `vi.waitFor` polled for the task + `last_fired_at` on disk. Both visible after `recordFired`'s disk write but BEFORE `arm()` runs in the next microtask. Test promise chain could unwind between the two; `expect(armedCount).toBe(1)` ran against an empty timers map.

Fix: fold the `armedCount` check into the `vi.waitFor` body. Polling all three observable effects (task on disk + last_fired_at on disk + timer re-armed) in one body removes the race. Confirmed: 5 consecutive clean full-suite runs after fix.

### #104 — Epic 9 Phase B substrate: encrypted credential vault

The substrate that unblocks OAuth flows. Same crypto pattern as the SCUT keystore (Epic 4 Phase A) in a separate namespace.

- **`src/runtime/credentials/types.ts`**: `CredentialMetadata`, `SealedCredential`, `PlaintextCredential` types. `CredentialVaultError` with codes (`NOT_FOUND`, `CORRUPT`, `INVALID_NAME`, `TAMPERED`, `IO_ERROR`, `INVALID_SECRETREF`). Slug rule `^[a-z][a-z0-9-]*$` for credential names.
- **`src/runtime/credentials/vault.ts`**: `CredentialVault` class. AES-256-GCM. Per-Agent wrapping key from HKDF(master_key, per-agent salt, info=`2200-agent-credentials-v1:<agent>`). Methods: `set / get / list / has / delete`. List returns metadata only; values stay sealed.
- **`src/runtime/secrets/types.ts`** + **`resolver.ts`**: `SecretRef.source` gains `vault`. `resolveSecret(ref, ctx?)` accepts an optional `{ home, agentName? }` context. Vault id parses as `<credential>` (uses default agent from ctx) or `<agent>:<credential>` (overrides). New error codes `VAULT_MISCONFIGURED` + `VAULT_MISS`. Existing `env` and `file` sources unchanged.
- **CLI**: `2200 credential set / list / show / delete`. `set` reads value from stdin so it never lands in shell history. `show` defaults to metadata-only; `--reveal` prints the value.
- **Tests**: 9 vault tests (round-trip, per-Agent isolation, GCM tag tamper detection, slug rejection, NOT_FOUND, idempotent delete, overwrite). 6 SecretRef-vault tests. 1 Identity loader test for `source: vault` acceptance.

## Decisions locked (session 5)

- **Vault namespace separate from SCUT keystore namespace.** Both derive wrapping keys from the same master key but use different per-Agent salts and different HKDF info strings. A salt compromise does not cross subsystems.
- **Credential names use the slug rule.** Same `^[a-z][a-z0-9-]*$` shape as Agent names + Skill / Extension names. Filenames stay safe across platforms; SecretRef ids stay parseable.
- **Vault SecretRef supports both bare and prefixed ids.** `vault:<credential>` resolves against the resolver context's default agent; `vault:<agent>:<credential>` overrides. The supervisor will pass `{ home, agentName }` when spawning an MCP server for a specific Agent.
- **`set` reads the value from stdin.** No `--value <secret>` CLI flag. Pipe the secret in (`echo "$TOKEN" | 2200 credential set ...`) so it never lands in shell history.
- **Phase B sub-phasing.** Substrate ships first (this PR). 9B-2 wires the OAuth flows. 9B-3 adds token refresh. 9B-4 wires `mcp_servers` env block to resolve vault refs at supervisor spawn time.

## In flight / known constraints

- **Plaintext master key on disk.** Documented v1 limitation; same posture as the SCUT keystore. Hardening to TPM / OS-keychain is post-launch.
- **Vault metadata is plaintext.** Listing without unsealing is the v1 design (small vaults, fast lists). Phase B can split metadata to a sidecar if listing speed matters at scale.
- **9B-2 OAuth flows assume an interactive shell + a browser.** The redirect server binds localhost only; for a headless server install, the operator copy-pastes a URL into a browser on another machine. Document this in the runbook when 9B-2 lands.
- **Token refresh in 9B-3 must not hold the master key in memory longer than necessary.** The vault re-derives per-Agent wrapping keys per call; refresh should follow the same posture.
- **Extension Phase B install hooks need a sandboxing decision.** Per the prior-art analysis, capability-restricted execution + Node-level isolation are architecturally load-bearing; the Phase B PR cannot hand-wave them.
