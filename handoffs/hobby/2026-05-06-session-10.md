### #129 ... server-side onboarding state machine

`runInterview` (Epic 14 Phase A) runs the interview as a single async function with a callback-driven `UserInput.ask()`. That shape works for stdin but not HTTP. PR #129 factors the interview into a discrete-step state machine that drives over HTTP request boundaries, while keeping the CLI's `runInterview` ergonomics unchanged.

What landed:

- **`src/runtime/onboarding/session.ts`** ... `OnboardingSession` class. State machine: `awaiting_opening` → `awaiting_branch_question` → `summarizing` → `done` → `confirmed` | `cancelled` | `errored`. `submitAnswer()` advances; `markConfirmed()` and `cancel()` lock the terminal states. Reuses `pickBranch` from the existing interview module + the same identity / tools / schedules builders so the resulting Agent matches what `2200 agent spawn` produces.
- **`src/runtime/onboarding/session-store.ts`** ... in-memory store with sliding-TTL cleanup. Default 30 min idle, 5 min sweep cadence. `register` / `touch` / `peek` / `delete` / `sweep` / `start` / `stop`. `start`/`stop` hook into the supervisor lifecycle.
- **Supervisor wiring** ... one `OnboardingSessionStore` per supervisor, exposed via `getOnboardingSessions()` so the HTTP server can register/touch sessions. Started on `Supervisor.start`, stopped on shutdown.
- **5 HTTP endpoints** under `/api/v1/onboarding`: POST (start), GET (resume), POST `/answer`, POST `/confirm`, DELETE (cancel). Schema endpoint enumerates them.

21 new tests (10 session, 7 store, 4 endpoint). 1252 runtime total.

### #130 ... web Onboarding Card Stack screen

The web client on top of #129's API. 4-phase driver: intro → interview → preview → confirmed.

What landed:

- Route `/onboarding`. Reachable via the new SPAWN link in the Fleet header.
- **Intro card**: explains the flow + Begin button. POST `/onboarding`. Surfaces `llm_provider_unavailable` (503) inline when the daemon has no API key.
- **Interview card**: question text, intent_tag chip, autosized textarea, Cancel + Next buttons. Renders an inline transcript of prior Q+A as the user goes. Server is the source of truth; the local mirror is best-effort and rebuilt from each response.
- **Preview card**: agent name, chosen branch, AI summary, suggested tools (with env hints + rationales), suggested schedules (cron + tz + rationale). Confirm + Cancel actions.
- **Confirmed card**: agent name, identity path, transcript path, continuity-note slug. Open Agent (jumps to `/agent/:name`) + Spawn-another buttons.
- `apps/web/src/lib/api.ts` ... 5 typed endpoints + wire shapes for Question, Transcript, Preview, Tool/Schedule suggestions, ConfirmResponse. Web client owns these declarations independently per the runtime/client boundary rule.

71 web tests passing on top of root's 1252.
