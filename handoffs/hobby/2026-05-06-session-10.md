### #129 ... server-side onboarding state machine

`runInterview` (Epic 14 Phase A) runs the interview as a single async function with a callback-driven `UserInput.ask()`. That shape works for stdin but not HTTP. PR #129 factors the interview into a discrete-step state machine that drives over HTTP request boundaries, while keeping the CLI's `runInterview` ergonomics unchanged.

What landed:

- **`src/runtime/onboarding/session.ts`** ... `OnboardingSession` class. State machine: `awaiting_opening` → `awaiting_branch_question` → `summarizing` → `done` → `confirmed` | `cancelled` | `errored`. `submitAnswer()` advances; `markConfirmed()` and `cancel()` lock terminal states. Reuses `pickBranch` + the same identity / tools / schedules builders so the resulting Agent matches what `2200 agent spawn` produces.
- **`src/runtime/onboarding/session-store.ts`** ... in-memory store with sliding 30-min TTL + 5-min sweep cadence. `start`/`stop` hook into supervisor lifecycle.
- **5 HTTP endpoints** under `/api/v1/onboarding`: POST (start), GET (resume), POST `/answer`, POST `/confirm`, DELETE (cancel).

21 new tests (10 session, 7 store, 4 endpoint).

### #130 ... web Onboarding Card Stack screen

The web client on top of #129's API. 4-phase driver: intro → interview → preview → confirmed.

- Route `/onboarding`. Reachable via the new SPAWN link in the Fleet header.
- Intro card: Begin button. Posts to `/onboarding`. Surfaces `llm_provider_unavailable` (503) inline.
- Interview card: question text, intent_tag chip, autosized textarea, Cancel + Next. Inline transcript of prior Q+A.
- Preview card: agent name, chosen branch, AI summary, suggested tools, suggested schedules. Confirm + Cancel.
- Confirmed card: agent name, identity path, transcript path, continuity-note slug. Open Agent → `/agent/:name`.
- 5 typed endpoints + wire shapes in `apps/web/src/lib/api.ts`. Web client owns these declarations independently per the runtime/client boundary rule.

### #133 ... Inbox filter bar + tier counts

The Inbox lists every pending notification across the fleet. Without filtering, that's noisy. The notifications API already supported `tier=` and `agent=` filters; #133 added the UI.

- **TIER chip group**: ALL, CRITICAL, IMPORTANT, NORMAL, each with a per-tier count from the unfiltered list (e.g. `CRITICAL · 2`). Counts stay accurate while a filter is active.
- **AGENT chip group**: ALL + one chip per agent with at least one pending notification. Renders only when 2+ agents have pending items, OR when the URL pre-selects one (graceful fallback when an agent named in `?agent=` has zero pending notifications: chip pre-selects with tooltip).
- **RESET** button on the right end clears both filters.
- **URL state**: `?tier=critical&agent=hobby` deep-links to a filtered view. AgentDetail's `INBOX →` link from #132 is the consumer (was added expecting #133).
- **Header subtitle** now reads `N pending (A critical · B important · C normal). Keyboard: ...`.
- **Differentiated empty state**: "no pending asks at all" vs "filter excluded everything" with a Reset-filters button on the latter.
- Single `unfilteredQuery` (drives counts + agent picker) plus a `filteredQuery` enabled only when a filter is active. Two queries dedupe at the TanStack Query layer.

CI hit a flaky failure on the first run (`tests/runtime/pub/wake-source.test.ts` ... unrelated to this PR's changes); root cause was a fixed 100ms sleep in a wait-until-enqueued check. PR #135 fixes the flake permanently. PR #133 retried green afterward.

### #134 ... Fleet empty-state Spawn CTA

When the user lands on `/` with no Agents, the empty state previously told them to use `2200 agent spawn` in their shell ... a dead end UI. #134 adds a primary `Spawn an Agent` button that navigates to `/onboarding`. Body copy now lists both paths (web flow + CLI). Two visible entry points (header SPAWN link from #130 + this empty-state CTA) cover both "I scan headers" and "I notice empty states" user behaviors.

Once any Agent is spawned, the empty state goes away but the header SPAWN link remains, so the user can always spawn additional Agents without re-finding the flow.

### #135 ... harden flaky pub wake-source unsubscribe test

`PubWakeSource > stop() unsubscribes; subsequent messages do not enqueue` relied on a fixed 100ms `setTimeout` to wait for the first message to route + enqueue. CI saw the assertion at length=0 before delivery. Every other "wait-for-enqueue" check in the file already uses a `waitFor` polling helper; the failing test was the only fixed-sleep outlier. Switched to `waitFor` for the first assertion; bumped the second (a "nothing happens" assertion, where fixed-timeout is the right shape) from 100ms to 200ms for headroom. 12/12 pass locally.

## Notes for future-me

- The Onboarding decision record (`2026-05-06-onboarding-driver-server-side-state-machine.md`) is the first time we've used "ship the substrate, name the augmentation path, defer the alternative architecture" as an explicit decision-record shape. Use this template for similar A-vs-B forks.
- The web Card Stack does NOT yet support session resume across page reloads ... session_id lives in component state. Easy add via query-string or sessionStorage if a real user complaint arrives. Intentional v1.
- The summary step on the final-answer endpoint runs synchronously inside `POST /onboarding/:id/answer` ... the user sees a 5-15s `Working...` button state during the LLM call. SSE upgrade is named in the decision record's unblock list, not on the immediate roadmap.
- `OnboardingSessionStore` shares sessions across all bearer-token holders on the same daemon. Fine for self-hosted; needs per-tenant scoping before managed-service launches (Epic 17 substrate).
- The `2200 agent spawn` CLI flow is unchanged ... Epic 14 Phase A's `runInterview` is byte-for-byte identical post #129. Only the new web flow uses the state machine.
- The flake in `tests/runtime/pub/wake-source.test.ts` is the second place this session where a fixed sleep failed under CI load. The `waitFor` helper is the right pattern; new tests writing "wait until <state>" should use it from the start. Fixed sleeps are appropriate ONLY for "wait to confirm nothing happens" non-event assertions.
- The Inbox filter bar uses URL query params (`?tier=&agent=`) for state, not React state. Lets AgentDetail's `INBOX →` link deep-link directly. Pattern is reusable for any future "filtered view" screens (Budget per-agent picker is a candidate).
- The command palette per-agent start/stop entries are gated by status and use a single `useMutation` keyed on the action verb. If we ever add a third action (e.g. `Restart <name>` or `Send <name> a message`), the same shape applies; just extend the action union.

## Reflection

Seven PRs in one session is a step beyond session 9's five. What enabled the throughput:

1. **Substrate-first ordering held.** Onboarding A (server state machine) before B (web Card Stack) before polish that depends on the routes/links existing (#131 adds `/onboarding` to the palette; #132 links to `/inbox?agent=` and `/budget?agent=` because those screens exist; #134 routes to `/onboarding` from the empty state). Each PR landed on top of an earlier PR's merged work without rebases.
2. **Decide-and-tell on the unblock vs. surface call.** "Circle back to B" was ambiguous. Picking "ship the substrate, write the decision record with named unblocks, defer parallel architecture" was an architectural call that an Agent in the build phase should make (per the decide-and-tell-in-build-phase memory) ... and the decision record means future-me or future-Doug has the receipt.
3. **Strict UI-only / runtime-only separation per PR.** Each polish PR (#131, #132, #133, #134) touches only `apps/web/`. The flake fix (#135) touches only `tests/runtime/`. No accidental coupling, no PR-pair-required merges.
4. **Verify-clean discipline at every commit.** Caught one ESLint rule (`@typescript-eslint/no-redundant-type-constituents`) and one prettier formatting issue early enough to fix in-place rather than discovering on PR CI.
5. **Flaky test caught and fixed in one session.** Rather than hand-wave the #133 CI failure as "intermittent," investigated, found the fixed-100ms-sleep antipattern, fixed it in a separate small PR (#135), and updated future-me notes to use `waitFor` from the start. Compounding benefit: the test stays green next time.
6. **Loop discipline.** Used `/loop` to chain wakeups while CI ran in the background. Each wake checked PR state, picked the next polish item (or alternate when the loop's default was already shipped), and avoided duplicate work even when stale loops fired.
