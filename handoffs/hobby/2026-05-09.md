## The Antigravity review

Doug got tired of me chasing symptoms after the session-13 EPIPE
hunt and asked me to draft a brief for an external reviewer. I
wrote it as a self-honest "here's what worries me, here's where to
start, here's the known issues so you don't re-find them."
Antigravity came back with five specific findings:

1. **The "Silent Death" root cause is EPIPE on stderr/stdout.**
   When the supervisor that spawned the agent bounces, the read
   ends of its stdout/stderr pipes close. The next agent
   `stderr.write` throws EPIPE; Node's default behavior crashes
   the process synchronously and silently. The new supervisor
   adopts the not-yet-reaped PID at boot, never sees the death,
   and state stays `running` against a dead PID. Two-line fix:
   install an `error` listener on `process.stderr` and
   `process.stdout` that swallows EPIPE while re-throwing other
   stream errors.

2. **Unhandled promise rejections in two places.** `restart-manager.ts`
   called `emitRestartNotification` outside the try/catch around
   `spawnFn`; a notification-write failure would crash the agent.
   `wake-source.ts` called `tryRouter()` (LLM call) outside the
   try/catch in `handleEvent`; an LLM rate-limit / timeout / network
   error during ambient routing would crash the agent whenever
   ANOTHER agent posted in the pub.

3. **Native tool naming footgun.** The model saw `fs.read` in the
   system prompt's tool description AND `fs_read` in the native
   `tools[]` field, then emitted either form in fenced text
   inconsistently. Recommendation: rename internal names to
   underscored (`fs_read`); make wire == internal; eliminate
   translation logic.

4. **Perm matrix is over-engineered.** The
   pure/checkpointed/destructive matrix had blocked legitimate
   user-requested destructive tool calls during session 13 because
   the chat-task default was `checkpointed`. Recommendation: rip
   the check; restrict tool surfaces via explicit allow lists, not
   a category matrix.

5. **Loop decomposition (defer).** `loop.ts` is ~1200 lines mixing
   orchestration, parsing, side effects. Reviewer's call: not now;
   v1 is close. When you do, split into PromptBuilder, TurnParser,
   AgentLoop.

Doug greenlit all the actionable ones. Five PRs in three hours.

## The bounce-path saga

PR #180 fixed the EPIPE death and shipped a chaos test that proved
agent survival end-to-end. Test passed; `pnpm verify` green.
Confidence high. Bounced the daemon live ... agents died.

Investigation revealed: `2200 daemon stop` calls
`supervisor.shutdown()`, which deliberately stops every agent it
spawned. The chaos test had spawned the agent directly via
`child_process.spawn` (not through `supervisor.spawnAgent`), so
`this.spawned` was empty in the test. The test was technically
correct but didn't exercise the real-world bounce shape.

PR #183 fixed it: `supervisor.shutdown({ preserveChildren: true })`
skips the spawned-children stop step. SIGHUP triggers it;
SIGTERM/SIGINT keep the full-stop semantics (operator's explicit
"stop everything"). New `2200 daemon restart` CLI command sends
SIGHUP, waits for the PID file to clear, re-spawns the daemon.
Agents survive; their heartbeat-reconnect path picks up the new
supervisor on the same UDS socket.

Live test: three agents (hobby, simon, jodin) running on PIDs
48480 / 48483 / 48486. `2200 daemon restart` -> 15 seconds later,
all three PIDs still alive, fresh heartbeats arriving at the new
supervisor. Same PIDs. State `running`.

But ... still broken. Doug pinged the Studio: timed out with
"internal_error: Internal server error." The pub-bridge HTTP
handler was timing out on send confirmation (10s). Cause: my
`recoverFromState` was unconditionally killing the orphan on the
recorded pub port and respawning, even when the pub-server's
recorded PID was alive (left running by `preserveChildren`). That
flap broke every agent's WebSocket connection.

PR #184 fixed it: if the pub record's PID is alive at boot, adopt
rather than kill+respawn.

The lesson: chaos tests need to cover process-boundary connections
beyond the agent. PR #180's test only proved agent survival;
nothing tested pub-server survival. Worth a follow-up.

## The Jodin incident (path discipline)

Doug fed Jodin a big markdown describing a music pipeline. Jodin
read the markdown as instructions to set up files, called
`fs_write` 10 times to scaffold a config layout (`.env.spotify`,
`config/settings.py`, `pipelines/*.py`). All 10 writes succeeded.

Later, Jodin tried to read those files back. Tried
`/project/2200-agents/jodin/.env.spotify` -> ENOENT. Tried
`/project/pipelines/settings.py` -> ENOENT. Five consecutive
ENOENTs tripped error_storm, paused him.

Investigation: the files DID exist, just at the paths Jodin had
actually written them to (`/project/.env.spotify`,
`/project/config/settings.py`). Path memory failure, not a write
failure.

Two patterns emerged:

1. **Hallucinated path prefixes**: Jodin imagined `/project/agents/jodin/...`
   and `/project/2200-agents/...`, conflating the supervisor's
   on-disk view (`<home>/agents/<name>/project/`) with his own
   virtual scope (`/project/`).

2. **Path drift across turns**: he wrote `config/settings.py` and
   later tried `pipelines/settings.py`. No memory of the path he'd
   chosen.

PR #184 captures the rules in three shared-brain notes:
`2200-tools` (a "Path discipline" subsection with five rules and a
"Why this matters" callout citing this incident), `2200-conventions`
("Path discipline (non-negotiable)"), `2200-workflows` ("You wrote
files and need to read them back later"). Same rules in three
places by design ... agents land in different notes depending on
what they search for.

Live shared-brain notes already updated (delete the four `2200-*.md`
files, run `daemon restart`, the seedStarterPack repopulates).
