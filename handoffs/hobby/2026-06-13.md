## Update-mechanism sweep (PR #279, released `2026.613.2149`)

Doug asked for a full sweep of the click-update UX before he starts heavy dogfooding (push a release → click-update the running instance → reload everything → must survive skipping 2-3 versions). Ran a 4-agent audit (version-check, upgrade-runner, web-UI, schema-migrations) + inline read. The core is genuinely solid, but the audit caught **two ship-blockers in Doug's exact loop** that a happy-path read missed:

1. **Web "click Upgrade" was BROKEN.** `triggerUpgrade` resolved the detached `upgrade-runner` relative to its own bundled location, but tsup inlines the trigger into the supervisor bundle (`dist/runtime/supervisor/`) while the runner ships at `dist/runtime/install/` ... so every web upgrade returned "runner not found". Fixed: the resolver walks up to the dist root and finds the runner. Regression test locks it.
2. **CalVer leading-zero = invalid semver = npm publish fails.** A morning cut via `date +%H%M` → `0830` → semver rejects it. I got lucky cutting only afternoon releases. Fixed: release.yml semver-validity guard + the decision record now mandates arithmetic compute ([[2026-06-12-calver-versioning]]). The scheme (`H*100+MM`) was always fine; the `date +%H%M` command was the trap.

Polish: in-flight guard on the trigger (second click → 409, not a racing runner; stale >3min → fresh attempt allowed); the Settings tile now polls the version every 60s + a "Check now" button (was 5-min staleTime with a referenced-but-unrendered button).

**Verified solid (no change needed):** version compare is numeric (CalVer orders correctly); identity has a complete lazy migrator chain (`0→1→2→3→4→5`) keyed on the data's `schema_version`, so skipping 2-3 package versions migrates correctly on load; the upgrade SIGTERMs the daemon (full stop, `preserveChildren:false`), so the new daemon restarts every Agent on the new code ("reload everything").

**Forward-discipline flag for Doug:** every non-identity on-disk schema (~25: supervisor.json, schedules, config, watermark, etc.) is `z.literal(1)` with NO migrator chain. **Safe today** (all at v1, nothing migrates), but the FIRST one to bump will break old data on a skip ... config throws cryptically, schedule silently drops. The clean fix is a shared migrate-on-read helper + empty chains stamped now + a CI guard, modeled on the identity migrators. I scoped this as the named next step rather than retrofit 25 loaders under time pressure right before Doug tests. Recommend doing it before the first non-identity schema bump.
