# Hobby's session 2026-05-15 — credential_request lifecycle hardening (structural TaskBlocker + loop batch dispatch fix + permanent refusal rule)

Doug opened with the observation that the credential request flow was still fundamentally broken: the Agent would re-ask for the same credential after it had already been fulfilled, spam tool calls while the operator was pasting the value, and fail to proactively confirm receipt without a nudge. The security property (the value never touches the Agent's loop or any LLM) was not visible to the operator. The goal for the day was a durable, structural fix that makes the flow "just work" for non-technical users while closing the security and trust gaps that frustrate OpenClaw users.

## What's true at the end of the day

- The re-ask after success is structurally prevented in most cases (permanent refusal at the tool level once any credential_request for a name has been fulfilled in the task).
- The "while pasting" tool spam is stopped (direct store check in the loop for any pending credential_request for the Agent).
- The input is always masked (`type="password"` on credential_request cards).
- The Agent is forced to do the post-fulfill `credential_has` to verify.
- The Agent is blocked from doing anything else (including re-asking or shell hunting) until it produces a real final assistant message (TaskBlocker in `verification_complete_awaiting_final_reply` state).
- The card shows the security language ("This value is sealed directly into the Agent’s encrypted vault. The Agent will never see it.") and a clean "Provided" state after the operator clicks Provide.
- Remaining gap: the Agent still does not proactively produce the final assistant confirmation message after the post-fulfill `credential_has` without a human nudge. The blocker prevents bad behavior, but the model is not yet closing the loop on its own.

## Today's work (high level)

The day was a long diagnostic and implementation session that moved from "more guards and prompt tweaks" to a proper structural solution.

**Key architectural decision (documented in `wiki/decisions/2026-05-15-taskblocker-subsystem.md`):**

We introduced a first-class `TaskBlocker` subsystem (new file `src/runtime/agent/blockers.ts`, `TaskBlockerRegistry`) instead of continuing to layer defensive code inside the 2000-line `AgentLoop`.

- Any human or external gate (`credential_request`, future `notification_ask`, voice confirmation, etc.) registers a `TaskBlocker`.
- The `AgentLoop` refuses new model calls and new tool dispatches while any blocker is active for the current task.
- The blocker is resolved only when the human/external event completes (fulfill, decline, timeout, or — for the credential flow — when the Agent produces a final assistant message after the post-fulfill `credential_has`).

**Loop batch-dispatch fix (the root cause of the re-ask in the same response):**

In `AgentLoop.run()`, the `for (const call of parsed.calls)` loop now checks `this.blockers.hasActive()` after *each* `runOneCall`. If a blocker is active, the remaining tool calls in that batch are dropped and the loop returns `{ kind: 'blocked_on_user' }`. This prevents the model from emitting `credential_has` + `credential_request` in the same response and having both execute.

**Permanent refusal rule at the tool level (the durable "no re-ask after success" guarantee):**

In `credential_request` (`doCredentialRequest`), we refuse with `decline_reason: 'credential_protocol_complete'` (and append guidance) if any request record for this agent + normalized credential_name has a non-null `fulfilled_at` (or is in any fulfilled state) in this task. This is checked as early as possible and uses the store as the source of truth. Once the operator has provided a credential for a name in the task, the Agent is not allowed to ask for it again.

**Direct store check in the loop for pending requests (stops "while pasting" spam):**

In addition to the TaskBlocker registry, the loop now does a direct `CredentialRequestStore.list({ agent, state: 'pending' })` right before every model call. If any credential_request for the Agent is still pending, the loop returns `blocked_on_user`. This stops the Agent from generating new tool calls while the operator is still in the fulfill flow, independent of the blocker registry wiring.

**`credential_has` ensures the 'awaiting final reply' blocker (makes the post-fulfill blocking reliable):**

After a successful post-fulfill `credential_has` for a name that has a fulfilled request record, the tool now ensures a blocker in `verification_complete_awaiting_final_reply` state exists for that name (creating one if none is found). This guarantees the loop stays blocked until the Agent produces a final assistant message, regardless of previous blocker ID or exact name string.

**Frontend Hybrid UX (card as primary feedback surface):**

- The `CredentialRequestCard` now shows the security language ("This value is sealed directly into the Agent’s encrypted vault. The Agent will never see it.") on the input form.
- After the operator clicks Provide, the card immediately shows a clean "Provided – sealed to the Agent’s private vault. The Agent has been instructed to verify receipt." state (instead of raw tool chips).
- The Agent is still forced by the TaskBlocker to produce a clean final assistant message in the chat confirming receipt + timestamp + readiness via `http_request` with `bearer_credential`.
- Input is always masked (`type="password"`).

**Wiring and paper trail:**

- The `TaskBlockerRegistry` is now a single shared instance created in `AgentProcess` and passed to both the `AgentLoop` and the baseline tool factory (via `getBlockerRegistry`).

## Evening continuation — TaskBlocker kind split + post-credential_has stall fix

Doug + Grok continued the work after the handoff above and tightened the prompts / guidance, then handed off to a fresh Hobby session to address the root cause they'd identified: the existing `TaskBlocker` mechanism conflated "we are waiting for an external party" with "we are waiting for the agent to speak," and used a single top-of-loop check for both. The post-`credential_has` blocker (registered to force the final reply) was therefore *preventing the very model call* that would produce that reply ... the loop bailed with `blocked_on_user` before the model was ever asked.

### Diagnosis (the contradiction)

- `credential_has` succeeds → registers a `verification_complete_awaiting_final_reply` blocker.
- Top of next loop iteration: `if (this.blockers.hasActive()) return blocked_on_user` fires.
- The model never gets called. The operator has to nudge to wake the agent so it can speak.

### Fix

Tiered `TaskBlocker` semantics so the model-call gate is intent-aware (intent-naming over behavior-naming, per Doug's feedback mid-session):

- `kind: 'human_gate'` (operator pasting, voice confirmation, external event): top-of-loop check returns `blocked_on_user`. New model calls and new tool dispatches both refused.
- `kind: 'awaiting_completion'` (model owes a final assistant reply): top-of-loop check is *permissive* ... the model is called. The for-loop mid-batch check breaks if a tool was dispatched while this blocker is active. If the model emits tool calls instead of speaking, an incomplete-turn-style nudge is pushed into history and a counter increments; on exhaustion of `DEFAULT_INCOMPLETE_TURN_RETRY_BUDGET` the loop throws so the operator sees a structured failure, not a silent stall. Resolved on the first text-only `done` response.

`credential_request` simplification: when the operator fulfills, the human_gate blocker is now *resolved* (not re-registered as `fulfilled_pending_verification`). We no longer try to force `credential_has` via the blocker mechanism ... that conflated two responsibilities. The prompt rule + the claim-vs-evidence audit already cover "the agent should call `credential_has` after fulfillment." The blocker is reserved for "you've finished the substantive work, now SPEAK to the operator," which is what `credential_has` itself registers on success.

### Live test result + the second bug we caught

First post-fix live test on simon errored with `Cannot read properties of undefined (reading 'class')` (a TypeError surfacing in the chat as the assistant's "reply"). Root cause: zombie agent processes ... 19 of them across simon/hobby/jodin had been re-registering against successive daemons over the prior several hours. The most recently-registered process "won" the supervisor's view but was running pre-fix code. `pkill -TERM -f agent/bootstrap.js` after a clean daemon stop, then `daemon start` + per-agent start, gave a clean 3-process fleet on the new dist. Worth surfacing as a Simon-side ask: the daemon's "agent already running" check on `agent start` should probably be tightened, or `daemon stop` should kill agent children unless explicitly preserved.

Second test (smart-bannana-api) ran the full credential lifecycle correctly: agent called credential_has, then credential_request, operator pasted, agent called the post-fulfill credential_has, the task transitioned to `done` with a clean final summary in `task.outcome.summary` ... but no assistant message appeared in the chat thread. The `outcome.summary` had exactly the message we wanted (`"Got it. The credential smart-bannana-api was provided by the operator, sealed into my vault, and verified present at ..."`). The watcher in `src/runtime/http/server.ts` (`watchAndAppendChatThreadReply`) was checking `messages.some((m) => m.task_id === taskId)` to avoid double-appending. That check matches the system-role envelope card the `credential_request` tool inserts AND the post-fulfill guidance messages, both of which carry the same taskId. So the watcher saw "already appended" and bailed before writing the assistant reply.

Fix: restrict the idempotency check to assistant-role messages only. Same one-line fix applied to both the legacy single-chat watcher and the multi-chat watcher.

Third test (dumb-bannana-api) was the clean run: probe credential_has → credential_request → paste → post-fulfill credential_has → final assistant reply *unprompted*: "Got the dumb-bannana-api credential. Verified in vault since 2026-05-15T21:11:44.922Z ... it's on disk, sealed and ready for use. No further work tied to it; I'm set whenever you need it." No nudge, no loop, no shell hunting.

The system-role guidance messages (post-fulfill and post-`credential_has`) now appear in the chat thread above the final assistant message. They were always being inserted as runtime scaffolding, but the watcher bug meant they didn't matter ... now they do, and they're visually noisy. Polish follow-up: either hide system-role guidance from the chat render or stop persisting them to chat once the prompt is doing its job. Not blocking.
