### Chat-task perm fix (commit 6)

- The dispatcher's `idempotency_compatible` check enforces a matrix:
  `pure` task -> pure tools only; `checkpointed` task -> pure +
  checkpointed; `destructive` task -> any. Chat-originated tasks
  defaulted to `checkpointed`, which blocked every destructive
  baseline tool (`schedule.add`, `schedule.run_once`, `shell.run`,
  `fs.delete`, `brain.delete`, etc.).
- Bumped chat-task default to `destructive`: a user asking via chat
  is implicit authorization to do whatever's needed. Orientation task
  seed in `migrateFromHandoff` also bumped to destructive (was
  defaulting to pure, would have blocked `brain.write_shared` and
  `chat.send` calls).
- Surfaced live: Doug asked Jodin to add a schedule via chat, three
  attempts hit the perm wall. Now resolved.

### Schedule.add timing flatten (commit 7)

- Discriminated union on `timing: { kind: 'cron' | 'interval', ... }`
  was breaking DeepSeek and Grok. Five consecutive ToolArgsErrors
  tripped Jodin into `blocked_on_detector` (error_storm).
- Flattened to top-level optional `cron` / `timezone` /
  `interval_seconds` with a refine: "exactly one of cron or
  interval_seconds." The supervisor RPC contract is unchanged; the
  tool execute() rebuilds the discriminated-union shape from the flat
  args.
- Sparked the convention note (see below).

### Cross-model tool-use hardening (commit 8)

Three sub-pieces, the durable architectural fix:

1. **Loop-side rescue**: `TOOL_BLOCK_RE` no longer requires `\n`
   before the closing fence (`}` followed directly by ``` parses
   now). New `extractToolShapedJson` fallback scans response text
   for any balanced `{...}` JSON object whose top-level looks like
   a tool call, regardless of fencing. Rescues bare-JSON output,
   mis-tagged ```json fences, JSON wrapped in prose. No-op when the
   response is genuinely a final answer.
2. **Native tool-use adapter**: CompletionRequest gains optional
   `tools: NativeToolSpec[]`; CompletionResponse gains optional
   `toolCalls: NativeToolCall[]`. Anthropic forwards as
   `tools: [{name, description, input_schema}]` and parses
   `tool_use` content blocks. OpenAI forwards as
   `tools: [{type: 'function', function: {...}}]` with
   `tool_choice: 'auto'` and parses `message.tool_calls`. New
   `src/runtime/llm/tool-spec.ts` builds the spec list from the agent's
   tool registry via Zod 4's built-in `z.toJSONSchema()` (no new
   deps). Agent loop prefers `response.toolCalls` over text-fenced
   parsing when present.
3. **Wiki convention**: `wiki/conventions/tool-schema-design.md`
   codifies the rules learned the hard way.

### Wire-name translation (commit 9)

- Anthropic and OpenAI both validate tool names against
  `^[a-zA-Z0-9_-]+$`. Our dotted internal names (`fs.read`,
  `brain.search_shared`) violate it. The first version of the native
  tool-use rollout broke every agent on this install with
  `Invalid 'tools[0].function.name'` 400s ... DeepSeek is
  OpenAI-compatible and validates the name pattern even though it
  doesn't actually wire function calling through.
- Fix: bidirectional name translation. `toNativeToolSpecs()` emits
  wire names with dots replaced by underscores (`fs.read` ->
  `fs_read`); each NativeToolSpec carries an `internalName` field
  with the dotted form. The agent loop, when promoting
  `response.toolCalls` into the parsed-call shape, looks up each
  call's wire name in the spec list and translates back to
  `internalName` before dispatching.
- Caught at runtime by Doug ("Nobody is responding in the Studio");
  fixed in real time within a couple of minutes after he flagged it.

The lesson lands as a process improvement in the convention note:

"validate against an actual API call before declaring native tool-use
ready" sub-rule, since unit tests with fake providers can't catch
provider-side validation.
