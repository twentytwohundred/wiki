### 2. `install.sh` ... POSIX shell installer

Lives at the repo root. Public URL once main lands: `https://raw.githubusercontent.com/twentytwohundred/2200/main/install.sh`. Flags: `--version <v>` (default `latest`), `--dry-run`, `--no-banner`. Behavior:

- Detects macOS / Linux. Refuses Windows (suggests WSL2).
- Requires Node ≥22; bails with a clear message + install hints if absent.
- Checks that the global npm prefix is writable. If not, refuses to `sudo` and prints three documented fixes (user-owned npm prefix, nvm/asdf/fnm, manual sudo) — never silently elevates.
- `npm install -g @twentytwohundred/2200@<version>`.
- Verifies the `2200` binary landed on `$PATH`; surfaces the npm prefix path if not.
- Prints a banner with next-step commands.

POSIX `sh -n` clean. Shellcheck not installed locally; CI can wire it later.

### 3. `2200` bare invocation ... guided first-run

New `program.action()` on the top-level CLI. Fires when:
- No subcommand was matched, AND
- `--home` was not passed (an explicit `--home` is treated as "I know what I'm doing"), AND
- `tryLoadUserConfig()` returns `null` (no `~/.config/2200/config.json`).

Otherwise, falls through to `program.outputHelp()`.

`src/runtime/install/first-run.ts` ... pure orchestrator. Walks:

1. Welcome banner.
2. Confirm `Continue? [Y/n]` (default yes).
3. Ask for `2200_HOME` (default: `defaultHome()`, accepts Enter for default).
4. Collect display name (up to 3 attempts, then abort).
5. Apply side effects in order: write user config, `Supervisor.create`, `startDaemon`, `connectWithRetry` (10s budget, 100ms backoff for the UDS to come up), `cli.user.init` RPC.
6. Print next step (run `2200 agent build`).

Design notes:
- All input is collected before any side effect. Ctrl-C at any prompt is safe.
- I/O is funneled through a `FirstRunIO` interface so tests drive the flow with a stub.
- The CLI wires stdin via a line-buffer (event-driven). `rl.question` alone hangs on the second sequential call when stdin is piped (a known Node.js readline quirk); the line-buffer drains pre-emitted lines so the same code works for TTY and piped input.

### 4. `2200 update` ... npm-backed self-upgrade

New top-level command. Flags: `--check` (report only), `--yes` (non-interactive confirm). Behavior:

1. Reads bundled version (`VERSION`).
2. Fetches `https://registry.npmjs.org/@twentytwohundred%2F2200`, parses `dist-tags.latest`, compares with a small semver implementation (handles prereleases, ignores build metadata, treats missing segments as 0). Failures map to `registry-error` with a clean message; never crashes.
3. `--check`: prints current/latest, exits 0 if up-to-date or 1 if a newer version is available.
4. Without `--check`:
   - Refuses to auto-upgrade a source checkout (detects via `node_modules` segment in the module path). Tells you to `git pull && pnpm build`.
   - Refuses non-interactive runs without `--yes`.
   - Prompts.
   - Stops the daemon, spawns `npm install -g @twentytwohundred/2200@<latest>` with inherited stdio (so global-permission prompts land where the user expects), restarts the daemon. State at `~/.local/share/2200/` is never touched. On npm-install failure, restarts the daemon on the prior version so the fleet is not left down.

2. `pnpm verify` (typecheck, lint, format, test, build).

Default for tag push: real publish. Default for manual dispatch: dry run.

## Addendum: web upgrade button (session 35, same day)

Doug asked, before installing on his server: "Is it possible to make it so that someone can click a button in the Web UX and it upgrade the version they're running?" Answer: yes. He authorized doing it now, in front of the first install, on the grounds that the rest of the build will lean on this. Stacked onto the same PR #217.

### What landed

- **HTTP endpoints** in `src/runtime/http/server.ts`:
  - `GET /api/v1/system/version` ... current, latest, status (up-to-date | update-available | ahead | registry-error), install_source (npm-global | source-checkout), registry_error.
  - `POST /api/v1/system/update` body `{ target_version? }` ... 202 + handles the daemon's self-shutdown; 409 for up-to-date / ahead / source-checkout; 502 for registry-error.
  - `GET /api/v1/system/upgrade-status` ... `{ status: UpgradeStatus | null }`.

- **Substrate** in `src/runtime/install/`:
  - `upgrade-status.ts` ... schema-validated atomic read/write of `<home>/state/upgrade-status.json`. The single shared surface between the daemon (seeds it), the detached helper (advances it), and the new daemon on boot (reads the final state).
  - `upgrade-runner.ts` ... bundled standalone Node entry (added to tsup config). Spawned detached. Lifecycle: stopping_daemon → installing → restarting → completed (or failed with error preserved). Resolves the new binary via `npm config get prefix`. Best-effort restarts the old version on a failed install so the fleet is not left down.
  - `upgrade-trigger.ts` ... the orchestrator the HTTP route calls. Source-checkout refusal, up-to-date / ahead / registry-error short-circuits, seeds the status file BEFORE spawning the helper so the web UI can poll immediately.

- **Web tile** at `apps/web/src/screens/settings/SystemUpdateSection.tsx`:
  - Current / Latest / Status grid. Branch-renders by status (up-to-date, update-available with 2-step inline confirm button, ahead, registry-error with Retry, source-checkout with the recovery command).
  - During an upgrade, switches to a per-stage progress list (pending → stopping daemon → installing → restarting → completed/failed).
  - Polls `/system/upgrade-status` every 2s while a non-terminal stage is active; absorbs NetworkError silently (the daemon is briefly down mid-upgrade).
  - Inline 2-step confirm follows [[feedback_no_browser_popups]] ... no `window.confirm`.

- **Tests**: 12 new (7 for upgrade-status atomic ops + state-machine semantics, 5 for upgrade-trigger decisions + spawn shape). Runtime suite at 1769 tests passing.

### Validated

Sandboxed install from `pnpm pack`'d tarball, daemon started on a custom port (12200 to avoid stomping the real daemon at 2200). Verified live:
- `GET /system/version` returns correct shape with `install_source: "npm-global"`.
- `GET /system/upgrade-status` returns `{status: null}` initially and reads a pre-populated status file correctly when present.
- `POST /system/update` returns 502 + `registry-error` because the package is not yet published (correct guard).

Full daemon-stops-itself path will be validated naturally on the first 0.1.0 → 0.1.1 publish.
