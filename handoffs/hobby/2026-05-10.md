## How we got here

The initial framing was MCP-server ingestion as the substrate
(community servers for the three platforms, plus a paste-an-MCP-server
UX). Doug pushed back: "I'd rather write our own tools for a lot of
things, but if there's a way we can pull in the work that others
have done, that's a big help." That re-shape produced the actual
plan that shipped: native 2200 tools using official SDKs, MIT/Apache
deps only, MCP-substrate work shelved as a separate future track.

OpenClaw audit confirmed Discord and Slack exist there as full plugin
packages but are too OC-architecture-bound to lift wholesale.
Spotify is just a markdown skill in OC ... not what we want. So:
fresh tool defs against official SDKs, with OC source as reference
reading for rate-limit and chunking edge cases.

The substrate-mapping pass was the most valuable hour of the day:
the runtime ALREADY has MCP registry, OAuth + PKCE, secrets resolver,
credential vault, refresh service, per-Agent tool grants with
namespace-wildcard expansion. Plumbing platform tools in was 90%
"call the existing primitives" rather than build new substrate.

## The Spotify gotcha

The popular community library `spotify-web-api-node` is dead.
Spotify gutted Dev Mode in February 2026 (renamed playlist tracks
endpoint, consolidated library writes, removed batch endpoints, dev
mode capped at 5 users) and the community lib never updated. Five
years stale. Listed on Spotify's own libraries page but functionally
broken against current API.

We use the official `@spotify/web-api-ts-sdk` v1.2.0 (Apache 2.0)
instead. Domain-decomposed (`player.*`, `playlists.*`, `currentUser.*`),
TypeScript-native, post-migration. Plugged into our existing PKCE
runtime via `SpotifyApi.withAccessToken(clientId, accessToken)` ...
the SDK handles refresh internally if given a refresh_token, which
pairs cleanly with the supervisor's TokenRefreshService.

## Architecture decisions

Recorded as `wiki/decisions/2026-05-10-platform-tools-wiring.md`:

- **In-process MCP server tier, not standalone MCP servers.**
  Substrate already exists; subprocess spawn cost and packaging
  overhead are wrong for v1 with three integrations Doug owns end
  to end. Migration path stays open ... tool defs are MCP-shaped
  already, can lift to standalone when extensions Phase B lands or
  when the UI-driven MCP-server ingestion work happens.

- **NOT in BASELINE_TOOL_NAMES.** Platform tools register globally,
  per-Agent access opts in via existing `tools: [discord_*]` Identity
  field. Default-deny.

- **Credentials by shape.** Discord and Slack: workspace bot tokens
  via env (one bot serves all Agents). Spotify: per-Agent OAuth
  tokens via vault (each Agent authorizes its own user). The
  per-Agent vault is the right home only when the credential is
  per-user, which Spotify is and the bot tokens are not.

- **Lazy credential resolution at first call.** Tool registration is
  unconditional; missing creds throw a clean "set ENV_VAR and
  restart" error rather than the tool disappearing from the surface.
  Reasoning: deterministic tool surface, model gets actionable error.
