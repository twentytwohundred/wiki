### Midday: morning playbook → Spotify breakage cascade

Cycled the fleet onto the new dist. Doug ran the playlist task ("clean it up to 10 + new cover art"). Cascade of distinct bugs surfaced:

1. **404 "Service not found"** ... Grok sent `Me/playlists` (capital M). Spotify case-sensitive. Fix: lowercase the leading path segment in `normalizePath`. `bef3cb9`.
2. **400 "Invalid limit"** ... search with `q: 'indie folk 90s OR 2000s'`. Spotify search doesn't support boolean operators; their error message names the wrong field. Enriched the error mapping + brain note. `bef3cb9`.
3. **`2200 oauth login` "missing OAuth client credentials"** ... CLI didn't load `runtime.env`. Fix: helper that loads both env files into `process.env` before the cred check. `9ea0b64`. Doug clicked the OAuth URL; fresh tokens landed.
4. **403 "Bad OAuth request"** ... model kept calling `/playlists/{id}/tracks`. That endpoint was deprecated in Feb 2026 for `/items`. SDK's hardcoded error message ("re-authenticating won't help") is misleading. Brain note catalog updated + error mapping detects the SDK's exact message and surfaces the real fix. `0184c0c`.
5. **413 Request Entity Too Large** on cover upload ... Spotify's 256KB cap is on the base64 body, not the raw JPEG. Cover tool was capping the raw at 256KB which expanded to ~341KB base64. Dropped raw cap to 190KB. `b375aaf`.

Each bug surfaced honestly via plan + run records in the brain. The new error enrichments from earlier in the day made subsequent debug cycles faster ... by the cover-cap fix the model was sending error text that directly pointed at the real cause.

## Things I'd flag if asked

The biggest pattern shift today was a meta-one: every time a fix tempted me to hard-code something operator-specific (named agents, specific brain slugs, specific scenarios), the right move was to push down one level to a platform primitive (fleet roster, brain-note naming convention, lane-agnostic phrasing). Doug caught this explicitly once ("we're building for us, not the masses"). I should pre-check for it every time a prompt-level rule or tool description is being added.

The platform-level rules landing in this session represent a different kind of v1 investment than yesterday's: yesterday added detectors and recovery loops, today added *teaching the agents to use what's already there*. That's lower-cost-per-unit-of-reliability than building more substrate. The brain notes + fleet roster + task delegation already existed. What was missing was the prompt-time instruction to actually USE them.

If tomorrow's test reveals rule 2 or rule 3 doesn't fire, the next escalation is **tool-description-level** teaching, not more system-prompt rules. The system prompt is for cross-tool discipline; the tool description is for tool-specific preconditions. Mixing the two has been a temptation today; resisting it.
