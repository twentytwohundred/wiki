# Epic 4.5: Cost caps and usage telemetry

User-configurable daily cost caps per Agent, plus a usage-telemetry surface that lets the user (and the Agent) see cumulative spend by session, day, week, month, broken down by Agent, provider, and model. Caps are mechanical at the supervisor layer: at 80% of cap a tier-2 notification fires, at 100% the Agent is blocked from starting new tasks until the cap resets or the user manually overrides.

This is the cost-control substrate that lets the seed team migrate into 2200 without burning the budget on a misconfigured router or a runaway tool loop.

## Why this epic

Six providers are wired (Anthropic, OpenAI, DeepSeek, Kimi, OpenRouter, Gemini). Multi-Agent coordination is working. The seed team is about to migrate into the platform. None of that is safe to run unattended unless the runtime knows how much each Agent is spending and refuses to overspend.

Three pieces have to be in place before the migration is safe:

1. **Per-Agent visibility.** "How much did Hobby cost today" answerable in one CLI command.
2. **Per-Agent ceilings.** Configurable daily cap that hard-stops new tasks when crossed.
3. **Threshold notifications.** Soft warning at 80%, hard stop at 100%, both via the existing notification file format.

Doug confirmed the shape on 2026-04-28: "Human gives each agent a cost cap for the day, and can adjust accordingly. There should be a dashboard like the one in Claude that tells you your usage stats per session/day/etc. That's already been solved. Let's just do that."

Pattern is lifted from Claude Code's per-session/day/week usage UI ([[license-posture]]: concept lift, no code copy). 2200's adaptation is per-Agent rather than per-account, since each Agent has its own identity, model picks, and tasks.

This epic builds on [[04-scut-identity-at-spawn]] for the per-Agent identifier. It also seeds the broader Agent Behavior settings dashboard surface flagged as a future epic in [[2026-04-24-cost-behavior-shape]] — cost caps are one of five eventual dimensions in that dashboard, but cost is the only one this epic implements.

## Scope

The deliverable is three things:

1. A `cost_caps` field in the Identity file that the supervisor enforces.
2. Per-call telemetry records persisted to disk, queryable by date / Agent / provider / model.
3. A `2200 usage` CLI command with the breakdowns Claude's usage UI offers, adapted per-Agent.

No web UI in this epic. The CLI is the surface for v1. The web/mobile dashboard lands when Epic 15 / 16 land; this epic ships the data layer those surfaces will eventually read from.

## Includes

### `cost_caps` field in the Identity file

```yaml
schema_version: 3  # was 2 after Epic 4; bumped again by this epic
name: hobby
# ... existing fields ...

cost_caps:
  daily_usd: 25.00         # required; hard ceiling per UTC day
  warn_at_pct: 80          # default 80; tier-2 notification threshold
  reset_at: "00:00 UTC"    # default UTC midnight; configurable to local TZ
  on_breach: "block_new_tasks"  # only behavior at v1; reserved for future "throttle" / "downgrade-tier"
```

`daily_usd` is the only required new field. Defaults for `warn_at_pct`, `reset_at`, and `on_breach` are documented in the schema and applied if absent.

**Why per-Agent in Identity, not global.** Per Doug 2026-04-28: Hobby and Simon will have very different appetites. Per-Agent in Identity makes the cap travel with the Agent across instances and across migrations. It also fits the [[2026-04-24-cost-behavior-shape]] "Per-Agent wallets" model (layer 6 in the eight-layer protection system) without going all the way to refilling-allowance semantics.

**Schema migration (2 → 3).** Existing Identity files (Hobby, Simon) get a default `cost_caps.daily_usd` of `$10.00` on first migration, with a Passive notification asking the user to set it explicitly. This default is conservative — at current Hobby cadence ($single-digit/day), it provides a real ceiling without being trivially blown through. Migration script in `src/runtime/identity/migrations/v2_to_v3.ts` with golden fixtures.

### Per-call telemetry capture

The LLMProvider abstraction's `complete()` call wraps every request with a telemetry-capture decorator. After the request returns (success or error), the decorator writes a record to the Agent's daily telemetry file:

```
state/telemetry/<agent_id>/2026-04-28.jsonl
```

Each line is one JSON object:

```json
{
  "schema_version": 1,
  "ts": "2026-04-28T15:23:14.521Z",
  "task_id": "task_01HJ...",
  "agent_id": "hobby",
  "provider": "anthropic",
  "model_id": "claude-opus-4-7",
  "input_tokens": 12453,
  "output_tokens": 891,
  "cached_tokens": 8200,
  "cost_usd": 0.0327,
  "status": "ok",
  "duration_ms": 4521
}
```

`cost_usd` is computed from `pricing.json` at write time using the input/output/cached token counts and the per-model rates. Errors get records too (with `status` set and `cost_usd` set to whatever the failed call did or did not consume — usually zero).

JSONL is the format because it is append-only, line-buffered, recoverable from partial writes, and trivial to query with `jq` / `grep` / a small Node parser. Per [[2026-04-24-brain-is-files-not-database]] discipline, telemetry is files first; SQLite indexing is a follow-on if query latency becomes a problem.

### Pricing table

`config/pricing.json` is the per-instance source of truth for "$ per million tokens" by provider and model. v1 is manually curated; the supervisor warns at startup if a model in use isn't in the table.

```json
{
  "schema_version": 1,
  "as_of": "2026-04-28",
  "models": {
    "anthropic/claude-opus-4-7": {
      "input_per_mtok_usd": 15.00,
      "output_per_mtok_usd": 75.00,
      "cached_input_per_mtok_usd": 1.50
    },
    "deepseek/deepseek-chat": {
      "input_per_mtok_usd": 0.27,
      "output_per_mtok_usd": 1.10,
      "cached_input_per_mtok_usd": 0.07
    },
    "openai/gpt-5": { "..." : "..." }
  }
}
```

The values here are illustrative. Doug curates the actual `pricing.json` from current public pricing pages. Auto-refresh from a pricing aggregator is out of v1 scope; if it becomes painful to maintain, that is a follow-on with its own decision record.

A model not present in `pricing.json` means the supervisor records `cost_usd: null` on telemetry but still tracks tokens. The next-day usage report includes a warning: "N calls to <model> have unknown cost. Add pricing entry to track."

### Budget tracking and enforcement

A `BudgetTracker` service runs in the supervisor process. On supervisor start, it:

1. Loads each Agent's `cost_caps.daily_usd` from Identity files.
2. Replays today's telemetry JSONL to compute cumulative spend per Agent.
3. Writes the cumulative state to `state/budget/today.json` (atomic temp + rename, like the rest).

After every model call (via the telemetry decorator):

1. The decorator increments the in-memory spend tracker for the Agent.
2. Persists the update to `state/budget/today.json`.
3. Checks thresholds:
   - Below `warn_at_pct`: nothing.
   - Crossed `warn_at_pct` (first time today): emit tier-2 notification "Hobby has used 80% of today's $25 cap ($20.07 of $25.00)."
   - At or past 100%: emit tier-1 notification, set the Agent's `budget_blocked: true` flag in supervisor state.

When `budget_blocked` is true:

- New task dispatches to the Agent fail with a clear error: "Daily cost cap exceeded; resets at <reset_time>. Override with `2200 agent budget override <name>`."
- The currently-running task, if any, finishes; the runtime does not interrupt mid-call. The next `complete()` after the over-cap one is the one that sees the block.
- Supervisor still wakes the Agent on schedule events to keep the loop alive, but the loop emits a Passive notification rather than dispatching a new task.

Reset semantics: at the configured `reset_at`, BudgetTracker rolls today's totals into a yesterday/historical record and starts a fresh `today.json` with zero spend per Agent.

**Override.** `2200 agent budget override <name> [--for-today | --for-N-hours <N>]` lifts the block for the configured duration. Logged with reason: "user override at YYYY-MM-DDTHH:MM:SSZ for <duration>". The override does NOT reset the cumulative; it just ignores the breach until the override expires. This matters because someone overriding for one hot task should not also unintentionally clear yesterday's overage from records.

**Manual reset.** `2200 agent budget reset <name>` zeros the cumulative for today. Logged. Reserved for cases where the user explicitly wants to start over (e.g., a broken pricing entry mis-reported costs).

### `2200 usage` CLI

Pattern-lifted from Claude Code's per-session/day usage UI ([[license-posture]] pattern lift, no code lift):

```
2200 usage                                # all Agents, today, summary
2200 usage --day                          # explicit (default)
2200 usage --week                         # last 7 calendar days
2200 usage --month                        # last 30 calendar days
2200 usage --since 2026-04-20             # custom start date
2200 usage --agent hobby                  # filter to one Agent
2200 usage --by task                      # one row per task (session view)
2200 usage --by model                     # one row per provider/model
2200 usage --by provider                  # one row per provider
2200 usage --json                         # machine-readable output
2200 usage --tail                         # follow live as records land
```

Default output (`2200 usage`) shows one row per Agent for today, with cumulative spend, the cap, and a progress indicator:

```
Agent     Spend     Cap       Pct    Tasks   Tokens (in/out/cached)
hobby     $4.32     $25.00    17%    14      1.2M / 89K / 800K
simon     $0.81     $10.00     8%     3      210K / 12K / 0
─────────  ─────────  ─────────
total     $5.13     $35.00    15%    17      1.4M / 101K / 800K
```

Color is used per [[design-language]] (familiar-analog UX): green under `warn_at_pct`, yellow at warn, red at or over cap. Color must have a non-color signal too (an asterisk or bracket) per [[2026-04-24-cost-behavior-shape]]'s color-blindness obligation.

`--by task` shows the session view:

```
Task                              Agent  Started   Duration  Spend     Model
task_01HJ...                      hobby  09:14     12m       $0.42     anthropic/claude-opus-4-7
task_01HK... (router)             hobby  09:18     <1s       $0.0008   deepseek/deepseek-chat
...
```

`--json` outputs the same data as parseable JSON for scripting.

### Notification messages for thresholds

Per [[2026-04-26-notification-file-format]], the notification objects emitted by BudgetTracker:

**Tier-2 (Important), at warn_at_pct first crossing:**

```yaml
schema_version: 1
tier: important
agent: hobby
title: "Daily cost: 80% of cap"
body: |
  Hobby has used 80% of today's $25.00 cap ($20.07).
  Remaining: $4.93 before new tasks are blocked at midnight UTC.
  
  Adjust the cap with `2200 agent identity edit hobby cost_caps.daily_usd`.
```

**Tier-1 (Critical), at 100%:**

```yaml
schema_version: 1
tier: critical
agent: hobby
title: "Daily cost cap reached: new tasks blocked"
body: |
  Hobby has reached today's $25.00 cap ($25.18).
  New tasks are blocked until 00:00 UTC (in 7h 23m).
  
  Override with `2200 agent budget override hobby [--for-today]`
  Adjust permanently with `2200 agent identity edit hobby cost_caps.daily_usd`.
```

These notifications respect the existing notification routing (currently file-based, will route through Epic 7 when Epic 7 lands).

## Done when

- A user can set a daily cap on any Agent via the Identity file and the supervisor honors it.
- A user can run `2200 usage` and see today's spend per Agent with the cap progress.
- A user can run `2200 usage --week --by model` and see a real breakdown of where the spend went.
- An Agent that crosses 80% of its cap fires a tier-2 notification exactly once that day.
- An Agent that crosses 100% of its cap is hard-stopped on new tasks until the cap resets, and a tier-1 notification fires.
- The override and manual-reset flows work as documented.
- Restart of the supervisor mid-day correctly recomputes today's cumulative from telemetry replay (no double-counting, no lost spend).
- Hobby and Simon both run a full day with caps in place and the cumulative numbers match a hand-tally from telemetry JSONL.

## Out of scope (deferred)

- **Layer 3 (anomaly detection):** comparing current task velocity to historical. Has to wait until there is enough historical data to baseline against. Follow-on epic.
- **Layer 5 (pre-flight prediction):** estimating a task's cost before starting. Useful but second-order; ships when the LLMProvider abstraction supports a `count_tokens` precall path uniformly.
- **Layer 6 (Per-Agent wallets with refilling allowances):** the cap in this epic is a hard daily ceiling, not a wallet that refills on a cadence. Wallet semantics are a follow-on epic.
- **Layer 7 (approval gating on expensive action types):** specific tools or task types requiring confirmation before running. Lives in the broader Agent Behavior dashboard epic.
- **Auto-refresh of pricing.json** from a pricing aggregator. Manual curation v1.
- **Web/mobile usage dashboard.** Lands when Epic 15 / 16 land.
- **Cross-Agent rollups for managed-service multi-tenant.** Lands when Epic 17 (managed service) lands.
- **Cost forecasting.** "At current rate, you will burn $X by month-end." Useful, follow-on.
- **Per-user balance enforcement (managed Tier 3).** This epic's caps are per-Agent. In the managed-tokens tier, the LLM proxy ([[../decisions/2026-05-05-managed-service]] § Provider key isolation) is the second-source-of-truth for token spend: it meters all calls across all of a user's Agents, applies the 12.5% markup, and deducts from the user's prepaid balance. The proxy enforces a per-user floor (service pauses at $1.00 remaining) independent of any individual Agent's per-day cap. Per-Agent caps remain useful for users who want a runaway-Agent firewall on top of the per-user floor. Lands with Epic 17.

## Upgrade-readiness

| Discipline | How this epic holds it |
|-----------|------------------------|
| Schema versioning | Identity bumps to v3 (cost_caps block). Telemetry records carry `schema_version: 1`. Pricing table carries `schema_version: 1`. All migrations have golden-fixture tests. |
| State on disk | Telemetry JSONL is append-only files. Budget cumulative state is `state/budget/today.json`. Atomic write pattern. |
| Restart safety | On supervisor start, BudgetTracker replays today's JSONL to rebuild cumulative state. No in-memory state is the source of truth. |
| Tool-call inspectability | Telemetry capture wraps every model call. Records are inspectable by date / agent / model. |
| Idempotent | Multiple BudgetTracker re-init runs converge to the same state because the source is the JSONL. |
| Inspectable artifacts | Every artifact (Identity, telemetry, pricing, budget state) is text-readable. |

## Notes

### Why not enforce mid-call

The decorator records cost after the call returns. A theoretically-cleaner design would estimate cost before each request and gate on the estimate, refusing the call if it would breach the cap. But:

- The estimate is only good for input tokens; output tokens are unknown until generation finishes.
- Many calls run in tight loops (router decisions, tool-use iterations). Pre-call gating adds latency to every request.
- The 80% warn threshold gives the user time to react before the hard stop.
- Tasks rarely have a single $5 call; they have hundreds of small calls. The cap is breached gradually, not all at once.

If a single call ever does threaten to blow past the cap by itself (a 200K-context Claude call, for instance), that is an Agent design problem, not a budget enforcement problem. Loop and stuck detection (Epic 2) is the layer that catches that.

### What "session" means in 2200

Claude's UI shows per-session usage where session = a chat. 2200's analog is per-task. The `--by task` view shows one row per task lifecycle. A long-running task (like Hobby's all-day Epic 3 build session) is one row in the task view; the per-day view aggregates many tasks.

### Wiring to Epic 7 when it lands

This epic emits notifications via the file-based interim mechanism from Epic 2. When Epic 7 (notification routing) ships, the same notification objects route through the proper tier-gated infrastructure with no changes to this epic's code. Per [[2026-04-26-notification-file-format]] discipline.
