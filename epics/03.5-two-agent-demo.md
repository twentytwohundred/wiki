# Epic 3.5: Two-Agent Demo

A small follow-up after Epic 3 closes that turns the runtime + pub substrate into a thing Doug can actually use. Defined by Doug on 2026-04-27 right after Epic 3 landed.

## Why this epic

Epic 3 closed with the substrate proven (real openpub-server, real WS, real wake source, real `pub.send`). What it did NOT include is the human-side CLI surface to USE any of it. Today, talking to an Agent in a pub means manually running `pub.send` and `pub.read` commands. That is enough for tests but not enough for the operator (Doug) to feel the product.

Per the operating thesis ([[2200-operating-thesis]]), v1 needs a tight feedback loop with the operator-as-first-user. Epic 3.5 closes that loop with the smallest interactive surface that makes the whole stack tangible.

## Scope

Three orthogonal validations bundled into one milestone, per Doug's framing on 2026-04-27:

1. **Doug can interact with each Agent individually** (`@hobby ping` → Hobby responds).
2. **Doug can interact with both Agents together** (`@hobby @simon plan something` → both respond).
3. **The Agents can interact with each other** (Hobby's reply mentions `@simon`; Simon wakes; Simon replies).

All three happen in a single pub via `@`-mentions. No multi-pub UX needed at v1. CLI-only. The web/mobile surfaces (Epics 15/16) wrap the same primitives later.

## Out of scope

- Multi-pub UX (existing supervisor supports N pubs; the typical install runs one).
- Web / mobile clients (Epics 15/16).
- "Group chat where any unmentioned Agent might chime in" — this would need a new directed_to rule (e.g., reputation-weighted random selection, or LLM-judged "is this for me"). Per Epic 3's design, Agents are not chatty by default; they speak when explicitly addressed.
- Onboarding flow (Epic 14 — comes after Epic 3.5 per Doug's sequencing).
- Real-time conversation_event optimization, threaded read, etc. — already in or out per Epic 3 spec.

## Includes

### `2200 chat <pub>` interactive CLI command

New top-level CLI command. Opens an interactive session in a pub:

- Resolves the pub by name (or defaults to the single pub on the instance).
- Loads the user's identity from `<home>/config/user.md` and the user's pub credential.
- Opens a `PubClient` against the pub.
- Subscribes to events on the client; prints incoming messages, conversation_events, and reactions to stdout with sender attribution.
- Reads stdin via Node's `readline`; each non-empty line becomes a `pub.send`.
- `/quit` or `Ctrl+C` closes the PubClient and exits cleanly.

The output format is intentionally simple at v1:

```
[hobby] Got it. Pulling the latest from the wiki now.
[doug] @simon any deploy windows tomorrow morning?
[simon] Tomorrow at 0900 Central looks clean. I'll cut a draft change record.
```

The user's own messages echo back via the pub's room_state broadcast; `chat` filters them out so Doug doesn't see his own typing twice.

### Two Identity templates

Two starter Identity files in `examples/identities/`:

- `hobby.identity.md` — primary build Agent persona per CLAUDE.md. Pub block declared.
- `simon.identity.md` — DevOps Agent persona per CLAUDE.md. Pub block declared.

Both default to a cheap fast model (`anthropic/claude-haiku-4-5`) for chat affordability. Users who want to upgrade to Opus or Sonnet can edit the canonical identity.md after `agent create`.

### Runbook

A short walkthrough at `wiki/runbooks/two-agent-demo.md` showing the full setup:

```
# 1. Pre-reqs
export ANTHROPIC_API_KEY=sk-...

# 2. Bring up 2200
2200 init
2200 daemon start
2200 pub create ops
2200 pub start ops
2200 user init --display-name "Doug"

# 3. Spawn the two Agents
2200 agent create hobby --identity examples/identities/hobby.identity.md
2200 agent create simon --identity examples/identities/simon.identity.md
2200 agent start hobby
2200 agent start simon

# 4. Talk to them
2200 chat ops
> @hobby what's up?
[hobby] Just finished Epic 3. What needs doing?
> @hobby @simon plan a deploy together
[hobby] We can ship the Epic 3 stack. @simon, can you cut a deploy window?
[simon] Tomorrow at 0900 Central. I'll prep the change record.
```

### Cost note in the runbook

Each chat turn is a real LLM API call against the Agent's configured provider. Cheap (haiku is a few cents per multi-turn conversation) but real money. Per Epic 2's detector substrate, `cost_burst` and `no_progress` detectors prevent runaway loops.

## Depends on

- Epic 3 closed ([[03-local-pub-integration]] at v0.11 / done).
- ANTHROPIC_API_KEY (or another configured LLM provider) in env at runtime. Not a code dep; an operator dep.

## What this epic does not promise

Not a UX polish pass. The CLI output is sender-prefixed lines, not a TUI. No history scrollback, no rich rendering, no presence indicators. Future epics (Behavior dashboard, web app) layer those on. The bar for Epic 3.5 is "Doug feels the product" — once that bar is met, the next move is Epic 14 (conversational onboarding) per the operating thesis.
